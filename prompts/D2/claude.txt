可以直接在 VS Code 里切换成白色主题,有几种方法,任选一种就行:

## 方法一:快捷键(最快)
按 `Ctrl + K`,然后紧接着按 `Ctrl + T`(按住 Ctrl 不松,先按 K 再按 T),会弹出主题选择列表。

## 方法二:菜单
顶部菜单栏 → **文件(File)** → **首选项(Preferences)** → **主题(Theme)** → **颜色主题(Color Theme)**

## 方法三:命令面板
按 `Ctrl + Shift + P`,输入 `颜色主题` 或 `Color Theme`,选中回车。

---

在弹出的主题列表里,选一个**浅色(白色)主题**,推荐这几个:

- **Light Modern**(浅色现代主题,背景接近纯白,界面最简洁)
- **Light+**(经典浅色主题)
- **Light (Visual Studio)**

用键盘上下键选,按回车就生效了,界面马上变白。

---

## 如果你还想更彻底的纯白

默认的浅色主题背景其实带一点点灰/蓝。如果你想要**完全的白色**,可以按 `Ctrl + Shift + P`,输入 `settings`,选「打开设置(JSON)」,在里面加这几行:

```json
"workbench.colorTheme": "Light Modern",
"workbench.colorCustomizations": {
    "editor.background": "#ffffff",
    "sideBar.background": "#ffffff",
    "activityBar.background": "#f0f0f0",
    "statusBar.background": "#ffffff",
    "statusBar.foreground": "#333333"
```

## (a) "平均一次" 是可以的，但你要清楚它的语义

把 `volatility_20d` 这一串平均，得到的是**"区间内滚动波动率的平均水平"**，这个数是合理的。但注意它**不等于**"整段数据的标准差"——因为每个 `volatility_20d` 本来就是"20 天窗口的标准差"，你再平均，是"标准差的平均"。

所以答辩时你要能说清：**"我这里的波动率，是区间内 20 日滚动波动率的均值"**，而不是含糊地说"这是区间波动率"。

| --- | --- | --- |

## (b) 为什么"最大回撤"要取**最小值**？—— 因为回撤是负数

这是最容易搞反的地方。关键：**`drawdown` 是负数，负得越多，代表跌得越惨**。

看具体例子。假设某股票 6 天的回撤序列是：

```
0,  -0.03,  -0.08,  -0.05,  -0.12,  -0.06
     跌3%     跌8%     跌5%     跌12%    跌6%
```

问："这只股票最惨的时候，从最高点跌了多少？"

答案是 **12%**，也就是 `-0.12`。

- `-0.12` 在这串数里是**最小**的（比 `-0.03`、`-0.05` 都小）
- 所以"最大回撤"= `min(drawdown)` = `-0.12`

如果反过来用 `max`，你会得到 `0`（第一天没跌），那完全没意义。

**一句话记牢**：回撤用负数表示"跌了多少"，"跌得最多"就是"数值最小"，所以 `max_drawdown = min(drawdown)`。立项报告 [5.3](证券金融数据分析与可视化系统_立项报告_v2.txt#L136) 也是这么写的。

| | Matplotlib | Plotly |

| 适合场景 | 导出到报告/论文 | **网页/看板** |

你们做的是 **Streamlit Web 系统**，用户要在浏览器里看数据、悬停看某天收盘价、缩放看某段——所以主战场选 **Plotly**。立项报告 5.2 和调研的 dashboard_stock 也都是 Plotly。

## 一句话心法

> **"暴露成参数" = 调用方每次可能想改的东西；"写死" = 全项目永远一致的东西。**

判断时问自己一句：**"这个值，如果 Role 1 用的时候想要不一样，我能不能不让你改代码就满足他？"**

- 能 → 做成参数（给个默认值）
- 永远一样 → 写死，但别散落各处，**抽进公共 theme 函数**

## 拿 `plot_price` 具体套一遍

**→ 暴露成参数（每次可能不同）：**

```python
def plot_price(df, show_ma=True, ma_windows=(5, 20), title=None):
```

- `show_ma`：有时只想看纯价格，有时想看均线 → 调用方想改
- `ma_windows`：可能想比 5/20 也可能想比 10/30 → 调用方想改
- `title`：不同页面标题不同 → 调用方想改

**→ 写死（全项目统一，抽进 theme）：**

- 配色（金融图一套固定色板）
- 字体、字号
- 轴标签叫法（"交易日期"、"收盘价"）
- 网格线、图例位置

这些谁来看都该长一样，就**不暴露**，统一写进 `_apply_theme(fig)` 里。

## 关键技巧：暴露的参数都**给默认值**

看上面那个签名——Role 1 什么都不传，`plot_price(df)` 也能直接用（默认画均线、5/20、无标题）；想自定义就传。这叫**"开箱即用，又可定制"**，是可复用函数的精髓。

你记住这条铁律就行：

> **可改的 → 参数 + 默认值；不变的 → 抽 theme 写死。**

## 测试的核心：证明"算得对"，不是"能跑"

关键区别一句话：

- ❌ **弱测试**：只断言"函数返回了一个叫 `return` 的东西"——就算你内部把收益全填成 0，测试照样过，等于没测。
- ✅ **强测试**：断言"函数算出来的值 == 我手算的预期值"——这才证明算对了。

**怎么做到强测试？用"你自己造的固定小数据"，而不是 demo CSV。**

原因：demo CSV 数据是现成的，但你**事先不知道正确答案**，就没法断言"等于多少"。而你**自己造一个 5 行的数据**，就能**先用手算**出答案，再让测试去比对。

看一个具体例子：

```python
# 造一个极小数据：3 天收盘价 100 → 110 → 121
# 手算日收益：
#   第2天 = 110/100 - 1 = 0.10
#   第3天 = 121/110 - 1 = 0.10
# 手算平均收益 ≈ 0.10

# 测试里就写：
def test_returns_analysis_average():
    result = returns_analysis(tiny_df)
    assert result["mean_return"] == pytest.approx(0.10)  # 断言等于手算值
```

所以测试要**两层**：

| 层 | 断言什么 | 作用 |
| --- | --- | --- |
| 结构 | 返回类型对、字段名对、行数对 | 保证"形状对" |
| 数值 | 关键数值 ≈ 手算预期（`pytest.approx`） | 保证"算得对" |
| 异常 | 空数据抛 `NoDataError`、缺列抛 `DataValidationError` | 锁定问题⑤的规则 |

## 一、eda.py —— 6 个分析函数

### 公共辅助：`_require_columns`（[第21行](stock-analysis-system/src/analysis/eda.py#L21)）

这是你所有函数的"守门员"，把之前问题⑤的异常规则**抽成一处**，避免每个函数重复写：

- 不是 DataFrame → `DataValidationError`
- 空数据 → `NoDataError`
- 缺必需列 → `DataValidationError`

**为什么这么设计**：6 个函数都要做同样的校验，抽出来就是"重构案例"——你答辩时可以讲"我把重复的校验逻辑抽成了 `_require_columns`"。

### 1. `describe_statistics`（[第36行](stock-analysis-system/src/analysis/eda.py#L36)）

- **输入**：含 `symbol` + 数值列的 DataFrame
- **做什么**：按股票分组，对数值列算 `count/mean/std/min/max`
- **输出**：index 是股票、列是 `(字段, 统计量)` 二级索引

**关键设计**（第46行）：`available = [c for c in columns if c in df.columns]` —— 指定的列如果数据里没有，就**跳过**，而不是报错。这样 Role 1 传入只有部分字段的数据也能用。

### 2. `date_range_summary`（[第54行](stock-analysis-system/src/analysis/eda.py#L54)）

- 每只股票输出三件事：`start_date`（最早）、`end_date`（最晚）、`n_rows`（有效行数）
- 用 `groupby` 的 named agg 一行搞定

### 3. `risk_return_summary`（[第64行](stock-analysis-system/src/analysis/eda.py#L64)）

**这是问题②的落地**，注意三个字段的取值：

| 字段 | 怎么算 | 对应你之前的决策 |
| --- | --- | --- |
| `mean_return` | `return` 的均值 | — |
| `volatility` | `volatility_20d` 的**均值** | 问题②「取平均」 |
| `max_drawdown` | `drawdown` 的**最小值** `min` | 问题②「回撤是负数，跌最深=数值最小」 |

### 4. `returns_comparison`（[第101行](stock-analysis-system/src/analysis/eda.py#L101)）

每只股票输出 4 列：`mean_return`、`cumulative_return`（区间累计收益）、`win_rate`（正收益天数占比）、`std_return`（样本标准差 ddof=1）。

三个小 helper（[第89-98行](stock-analysis-system/src/analysis/eda.py#L89)）专门抽出来，避免在 `agg` 里用 lambda（pandas 会对 lambda 告警）：
- `_cumulative_return` = `(1+return).prod() - 1`，且先 `dropna()` 排除第一天
- `_win_rate` = 正收益的比例
- `_std_return` = 标准差，**显式 `ddof=1`**（样本标准差）

### 5. `correlation_matrix`（[第121行](stock-analysis-system/src/analysis/eda.py#L121)）

**这是问题⑥（Spearman）的落地**：
- 第131行 `pivot`：把「长表」（一行一个交易日）转成「宽表」（行=日期、列=股票），这样 5 只股票的 return 才能两两算相关
- 第132行：少于 2 只股票 → `InsufficientDataError`（1 只股票算不了相关）
- 第134行：`corr(method="spearman")`，默认就是 Spearman

### 6. `missing_values_summary`（[第137行](stock-analysis-system/src/analysis/eda.py#L137)）

每列输出 `missing_count`（缺几个）和 `missing_ratio`（缺的比例）。这个函数**最宽容**——它统计缺失，所以不需要任何特定字段，任何 DataFrame 都能进。

## 一句话结论

## 先理解"分支(branch)"和"主线(main)"

Git 仓库不是只有一份代码，而是可以有多条"分支"。你们的团队约定（立项报告 6.3）就是：

```
Branch → Commit → Pull Request → Human Review → Merge
(开分支)   (提交)     (发合并请求)     (人工审核)     (合并)
```

- **main** = 主分支，相当于"正式版/主线"，大家最终都从这条线拉代码。
- **feat/data-foundation** = Role 2 的"工作分支"，他在这条分支上写数据层代码、提交，但这些改动**还没进 main**。

## 现在的状态是这样的

```
main  ──●────●────●────●────●────  ← 你的本地、GitHub 都停在这，src/data 还是占位符
            \
feat/data └────●────●────●────●   ← Role 2 在这条分支上提交了 fetch/clean/features
              (数据层代码都在这，但 main 里还没有)
```

Role 2 的代码已经写好了、也提交了，但**只存在于 `feat/data-foundation` 这条分支上**。main 里的 `src/data/*.py` 还是那个空占位符。这就是为什么你本地看到的还是旧的。

## "PR" 和 "合并 PR" 是什么

- **PR（Pull Request，拉取请求）**：Role 2 发起的一个请求，内容是"请把我的 `feat/data-foundation` 分支合并进 `main`"。
- **Human Review（人工审核）**：你们团队要求必须有人（通常是组长 Role 1，或相关 Owner）先看一遍代码、跑一遍测试，确认没问题。
- **合并（Merge）**：审核通过后，组长点"Merge"，`feat/data-foundation` 的改动就正式并入 `main`。这时候 main 里的 `src/data` 才变成真实现。

所以**"等 Role 2 正式合并 PR"** 就是：

> 等 Role 2 发起合并请求、组长审核通过、改动合进 main —— 之后你从 main 拉最新代码，才能拿到他的数据层实现。
